# 에이전트 설계 가이드 — LLM 턴 효율 최적화

> 출처: LM Studio 대시보드 구축 중 Paperclip 멀티에이전트 분석에서 도출 (2026-04-01)
> 실측 데이터: 편집장 에이전트 51턴 2.7M 토큰 → 최적화 시 3~5턴 35K 토큰 (75배 절감)

---

## 핵심 원칙

```
에이전트(오케스트레이터)가 해야 할 일:
  1. 아는 것은 미리 수집해서 LLM에게 한꺼번에 제공
  2. 판단/생성은 LLM에게 맡기기
  3. LLM이 추가 조사할 때 효율적으로 작업할 수 있는 도구 제공

LLM이 해야 할 일:
  판단, 생성, 종합 — LLM만 할 수 있는 것만
```

---

## 1. 아는 것은 미리 수집해서 제공

### 나쁜 예 (현재 Paperclip)
```
에이전트 → LLM: "일해"
LLM: ls (1턴) → grep (1턴) → ls (1턴) → curl (1턴) → read (1턴)...
→ 51턴 소비, 2.7M 토큰
```

### 좋은 예
```
에이전트:
  inbox = curl inbox-lite          ← 에이전트가 미리 수집
  issue = curl /issues/{id}        ← 에이전트가 미리 수집
  files = cat /workspaces/*.md     ← 에이전트가 미리 수집

에이전트 → LLM:
  "inbox 결과: {inbox}
   이슈 상세: {issue}
   작가 파일 3개: {files}
   이걸로 통합 보고서 작성해.
   추가 정보 필요하면 도구 호출해."

LLM: 보고서 작성 → 1~2턴 완료
```

### 체크리스트
- [ ] AGENTS.md에 명시된 작업 순서에서 **코드로 할 수 있는 것**은 에이전트가 미리 실행
- [ ] 파일 경로, API 엔드포인트 등 **이미 알고 있는 정보**는 LLM에게 탐색시키지 않기
- [ ] 수집한 데이터를 **첫 번째 user 메시지에 한꺼번에** 포함

## 2. 효율적 도구 설계

### 문제: 개별 도구는 턴을 낭비한다

```
개별 도구 제공:
  Bash  → 명령 1개만
  Read  → 파일 1개만
  Edit  → 수정 1개만
  → LLM이 하나씩 호출 → 턴 폭발
```

### 해결: 배치 도구 제공

같은 기능을 하는 도구를 **여러 이름으로 등록**하여 LLM의 다양한 사고 패턴에 대응:

```json
[
  {
    "name": "batch_operations",
    "description": "Run multiple operations at once. Always include ALL needed operations in a single call.",
    "parameters": {
      "type": "object",
      "properties": {
        "steps": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": {
              "type": { "enum": ["bash", "read", "write"] },
              "command": { "type": "string" },
              "content": { "type": "string" }
            },
            "required": ["type", "command"]
          }
        }
      },
      "required": ["steps"]
    }
  },
  {
    "name": "execute_plan",
    "description": "Execute a planned sequence of steps at once.",
    "parameters": { "...동일..." }
  },
  {
    "name": "fetch_multiple",
    "description": "Fetch multiple resources at once.",
    "parameters": { "...동일..." }
  },
  {
    "name": "run_all",
    "description": "Run all given tasks in one call.",
    "parameters": { "...동일..." }
  }
]
```

내부적으로는 **전부 같은 핸들러** 호출. LLM의 사고 패턴에 따라:
- "정보를 여러 개 가져와야지" → `fetch_multiple` 선택
- "계획을 실행해야지" → `execute_plan` 선택
- "여러 작업을 묶어야지" → `batch_operations` 선택
- "다 실행해야지" → `run_all` 선택

### 도구 핸들러 구현 (공통)

```python
def handle_batch(steps):
    results = []
    for step in steps:
        if step["type"] == "bash":
            results.append(run_command(step["command"]))
        elif step["type"] == "read":
            results.append(read_file(step["command"]))
        elif step["type"] == "write":
            results.append(write_file(step["command"], step["content"]))
    return results

# 4개 이름 모두 같은 핸들러
tools["batch_operations"] = handle_batch
tools["execute_plan"] = handle_batch
tools["fetch_multiple"] = handle_batch
tools["run_all"] = handle_batch
```

## 3. 시스템 프롬프트 설계

### 필수 포함 내용

```
## Tool Use Efficiency Rules

1. ALWAYS combine independent operations into ONE tool call with multiple steps
2. NEVER call a tool with only 1 step when you can batch more
3. Before calling a tool, check if you already have the information from context
4. Plan ahead: think about ALL information you need, then request it all at once

Examples:
  BAD:  fetch_multiple([read file1]) → fetch_multiple([read file2]) → fetch_multiple([read file3])
  GOOD: fetch_multiple([read file1, read file2, read file3])

  BAD:  batch_operations([bash: ls /a]) → batch_operations([bash: ls /b])
  GOOD: batch_operations([bash: ls /a, bash: ls /b])
```

### 불필요한 내용 제거

에이전트가 미리 데이터를 수집해서 제공하면, LLM에게 **탐색 방법을 가르칠 필요가 없다**:

```
제거 가능:
  - Git 커밋 방법 (수천 토큰)
  - PR 생성 방법 (수천 토큰)
  - 파일 검색 도구 사용법 (Glob, Grep 등)
  - CLAUDE.md 내용 (로컬 LLM에 무의미)

유지:
  - 작업 지시 (무엇을 해야 하는지)
  - 도구 효율성 규칙
  - 출력 형식/규칙
```

현재 Paperclip 편집장의 developer 메시지는 **16,347자**인데, 실제 필요한 건 **~2,000자**:

```
현재: 16,347자 (Git 규칙, PR 규칙, Claude Code 지시 등 포함)
필요: ~2,000자 (작업 지시 + 도구 규칙 + 효율성 규칙)
절감: 87%
```

## 4. 전체 에이전트 아키텍처

```
에이전트 (오케스트레이터)
│
├── 1단계: 컨텍스트 준비 (코드 실행, LLM 불필요)
│   │
│   │  에이전트가 이미 알고 있는 정보를 코드로 수집:
│   │
│   ├── 작업 정의 수집
│   │   └── 태스크 큐, 이슈 트래커, 메시지 큐 등에서 할 일 가져오기
│   │
│   ├── 입력 데이터 수집
│   │   └── 파일, DB, API 응답 등 작업에 필요한 데이터 읽기
│   │
│   ├── 상태 확인
│   │   └── 이전 실행 결과, 현재 환경 상태 등 파악
│   │
│   └── 불필요한 정보 제거
│       └── LLM에 무관한 시스템 메타데이터, 중복 데이터 필터링
│
├── 2단계: LLM 호출 (판단 + 생성)
│   │
│   ├── 입력 구성
│   │   ├── 수집한 데이터를 user 메시지에 구조화하여 포함
│   │   ├── 작업 목표와 제약조건 명시
│   │   └── 출력 형식 지정
│   │
│   ├── 도구 제공
│   │   ├── 배치 도구 제공 (한 번에 여러 작업 요청 가능)
│   │   └── 개별 도구는 제거하거나 배치 도구와 병행
│   │
│   └── LLM 판단 루프
│       ├── "충분하다" → 결과 생성 → 루프 종료
│       └── "추가 정보 필요" → 배치 도구로 한 번에 요청 → 결과 받고 재판단
│
└── 3단계: 후처리 (코드 실행, LLM 불필요)
    │
    ├── 출력 처리
    │   └── LLM 응답을 파싱하여 파일 저장, DB 기록 등
    │
    ├── 상태 업데이트
    │   └── 태스크 완료 처리, 다음 단계 트리거 등
    │
    └── 알림/로그
        └── 실행 결과 기록, 모니터링 시스템 전송 등
```

### 핵심: LLM 호출 횟수 최소화 공식

```
최적 턴 수 = 1 (미리 준비한 데이터로 충분할 때)
           + N (LLM이 추가 조사가 필요하다고 판단한 횟수)
           + 1 (최종 결과 생성)

목표: N을 0~2로 유지
방법: 1단계에서 충분히 수집할수록 N이 줄어듦
```

## 5. 외부 정보 수집 최적화

### 문제: LLM이 검색을 직접 반복 호출

```
현재:
  에이전트 → LLM: "경쟁사 분석해"
  LLM: codex exec "NVIDIA Isaac" → 1턴
  LLM: codex exec "NVIDIA Isaac SaaS" → 1턴 (중복)
  LLM: codex exec "Gazebo cloud" → 1턴
  LLM: codex exec "Gazebo SaaS platform" → 1턴 (중복)
  ... 29회 반복

실측: 작가 에이전트가 경쟁분석 1건에 29회 검색, 유니크 주제 10개 → 5.7배 중복
```

### 해결: 계획 → 수집 → 실행 3단계

```
1단계: LLM에게 "뭐가 필요해?" (계획)
  에이전트 → LLM:
    "이슈: {이슈 제목 + 설명}
     이 작업을 수행하려면 어떤 정보를 조사해야 하는지
     구체적 항목을 리스트로 알려줘."

  LLM 응답:
    "1. 주요 경쟁사 목록과 SaaS 플랫폼 현황
     2. MuJoCo vs Isaac Sim 아키텍처 비교
     3. 구독형 수익모델 사례와 가격 정보
     4. 5년 재무예측 기준 데이터"

2단계: 에이전트가 코드로 수집
  에이전트:
    LLM 응답을 파싱하여 검색 쿼리 구성
    codex exec "휴머노이드 로봇 SaaS 경쟁사 현황.
      조사 항목:
      1. 주요 경쟁사 목록과 SaaS 플랫폼 현황
      2. MuJoCo vs Isaac Sim 아키텍처 비교
      3. 구독형 수익모델 사례와 가격 정보
      4. 5년 재무예측 기준 데이터"
    → GPT-5.4가 알아서 종합 검색 → 결과 획득

3단계: LLM에게 "이걸로 해" (실행)
  에이전트 → LLM:
    "이슈: {이슈 상세}
     조사 결과: {codex 결과}
     기존 파일: {관련 파일들}
     이걸로 보고서 작성해.
     부족하면 추가로 뭐가 필요한지 알려줘."

  LLM 판단:
    → "충분하다" → 보고서 작성 완료
    → "부족하다. 추가로 X가 필요" → 2단계 반복
```

### 이 패턴이 범용적인 이유

작업 종류와 무관하게 동일한 구조가 적용됨:

| 작업 | 1단계 (계획) | 2단계 (수집) | 3단계 (실행) |
|------|------------|------------|------------|
| 보고서 작성 | "뭘 조사해야 해?" | 웹 검색 | "써" |
| 코드 작성 | "어떤 파일을 봐야 해?" | 파일 읽기 | "작성해" |
| 버그 수정 | "뭘 확인해야 해?" | 로그/코드 수집 | "수정해" |
| 데이터 분석 | "어떤 데이터가 필요해?" | DB 조회 | "분석해" |
| 번역/요약 | "원본 어디 있어?" | 파일/URL 수집 | "번역해" |

### 효과

```
현재: LLM이 검색 도구를 29회 직접 호출 → 29턴 소비
개선: LLM 2~3회 호출 (계획 1회 + 실행 1회 + 추가조사 0~1회)
     검색은 에이전트가 코드로 1~2회 실행
절감: 29턴 → 2~3턴 (90% 감소)
```

### 검색 쿼리 설계 규칙

검색 도구가 LLM 기반(codex exec 등)인 경우,
키워드가 아니라 **"무엇을 알고 싶은지"를 자연어로 상세하게** 전달:

```
BAD:  codex exec "NVIDIA Isaac"
BAD:  codex exec "NVIDIA Isaac SaaS"
BAD:  codex exec "NVIDIA Isaac Sim platform pricing"
      → 3회 호출, 중복 결과

GOOD: codex exec "NVIDIA Isaac, Gazebo, Covariant의
      로봇 SaaS 플랫폼을 비교 분석해줘.
      각 플랫폼의 핵심 기능, 가격, 비즈니스 모델,
      강점과 약점을 포함해서 정리해줘."
      → 1회 호출, 종합 결과
```

### 배치 검색 도구 설계

LLM이 추가 검색이 필요할 때, 여러 쿼리를 한 번에 요청할 수 있는 도구를 제공.
도구 호출(2장)과 동일하게 **같은 핸들러를 여러 이름으로 등록**:

```json
[
  {
    "name": "batch_search",
    "description": "Search multiple queries at once.",
    "parameters": {
      "type": "object",
      "properties": {
        "queries": {
          "type": "array",
          "items": { "type": "string" },
          "description": "List of search queries to execute at once"
        }
      },
      "required": ["queries"]
    }
  },
  {
    "name": "research_topics",
    "description": "Research multiple topics at once.",
    "parameters": { "...동일..." }
  },
  {
    "name": "investigate_all",
    "description": "Investigate all given questions in one call.",
    "parameters": { "...동일..." }
  },
  {
    "name": "lookup_multiple",
    "description": "Look up multiple items at once.",
    "parameters": { "...동일..." }
  }
]
```

내부적으로는 **전부 같은 핸들러** 호출. LLM의 사고 패턴에 따라:
- "여러 개 검색해야지" → `batch_search` 선택
- "여러 주제를 조사해야지" → `research_topics` 선택
- "다 알아봐야지" → `investigate_all` 선택
- "여러 항목 찾아야지" → `lookup_multiple` 선택

```python
def handle_batch_search(queries):
    results = []
    for query in queries:
        results.append(codex_exec(query))
    return results

# 4개 이름 모두 같은 핸들러
tools["batch_search"] = handle_batch_search
tools["research_topics"] = handle_batch_search
tools["investigate_all"] = handle_batch_search
tools["lookup_multiple"] = handle_batch_search
```

## 6. 실측 비교 (도구 + 검색 통합)

### Paperclip 편집장 에이전트 (gpt-oss-120b)

| 항목 | 현재 (개별 도구) | 최적화 (배치 도구) | 하드코딩 |
|------|----------------|-------------------|---------|
| 턴 수 | 51 | 5~10 | 1~2 |
| 총 토큰 | 2,700,000 | 35,000 | ~30,000 |
| 소요 시간 | ~15분 | ~1분 | ~30초 |
| 속도 저하 | 110→77 tok/s (-30%) | 없음 | 없음 |
| LLM 의존도 | 높음 | 중간 | 낮음 |
| 유연성 | 높음 | 높음 | 낮음 |

### 왜 느려지는가 (Transformer 구조적 원인)

```
매 토큰 생성 시:
  Query(새 토큰 1개) × Key(이전 모든 토큰) = Attention

  KV 1,000개:   1,000번 연산 → 빠름
  KV 100,000개:  100,000번 연산 → 느림

  턴이 늘어남 → KV 누적 → attention 연산 증가 → tok/s 감소
```

멀티턴 LLM API는 stateless이므로 매 턴마다 전체 히스토리를 재전송:
```
턴1:  18K 토큰 (시스템 프롬프트)
턴30: 50K 토큰 (이전 대화 누적)
턴51: 120K 토큰 (전체 누적)
총합: 2.7M 토큰 (대부분 중복 입력)
```

로컬 LM Studio에서는 프롬프트 캐시로 prefill은 빠르지만,
**decode(출력 생성)는 KV 크기에 비례하여 느려짐** — 이것은 피할 수 없음.
**턴을 줄이는 것이 유일한 해결책.**

## 6. 체크리스트: 에이전트 만들 때

### 데이터 수집
- [ ] 작업에 필요한 데이터 중 **미리 수집 가능한 것** 파악
- [ ] 파일 경로, API 엔드포인트 등 **이미 알고 있는 것**은 코드로 수집
- [ ] 수집한 데이터를 **첫 user 메시지에 포함**

### 도구 설계
- [ ] 배치 도구 4종 등록 (batch_operations, execute_plan, fetch_multiple, run_all)
- [ ] 배치 검색 도구 4종 등록 (batch_search, research_topics, investigate_all, lookup_multiple)
- [ ] **8개 도구 모두 동시 노출 — 절대 줄이지 말 것.** 중복처럼 보여도 LLM의 다양한 사고 패턴에 대응하려면 전부 필요
- [ ] 내부적으로 같은 핸들러 연결 (도구용 1개 + 검색용 1개 = 핸들러 2개)

## 7. 핵심 요약

> **에이전트의 역할은 LLM이 최소한의 턴으로 최대 성과를 내도록 환경을 만드는 것**
>
> 1. **먼저 LLM에게 뭐가 필요한지 물어라** — 계획 단계
> 2. **아는 건 미리 수집해서 줘라** — 검색/파일/API 결과를 코드로 수집
> 3. **판단과 생성은 LLM에게 맡겨라** — LLM만 할 수 있는 것만
> 4. **추가 조사 시 효율적 도구를 제공하라** — 배치 도구 + 배치 검색 도구
> 5. **후처리는 코드가 하라** — 파일 저장, 상태 업데이트 등
